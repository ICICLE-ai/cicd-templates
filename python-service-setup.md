# Setting Up an ICICLE Python Service

> Step-by-step instructions for onboarding a new Python service to ICICLE's CI/CD pipeline.

This guide walks you through everything you need in your service repo to get it building and deploying automatically. Plan on about 15 minutes end-to-end.

---

## Before you start

You'll need:

- A git repo for your service (empty is fine).
- [`uv`](https://docs.astral.sh/uv/) installed locally.
- Docker installed locally (for optional local testing).
- Your service's target Tapis pod name. Ask in `#icicle-service-support` if you don't have one yet.

---

## What you're building

By the end of this guide, your service repo will have:

```
your-service/
├── icicle-service.yaml    ← deploy config (you create)
├── pyproject.toml         ← Python deps + uv_build backend (you create)
├── uv.lock                ← generated by uv
├── entrypoint.sh          ← how your container starts (you create)
├── .dockerignore          ← copied from the template
└── src/
    └── icicle_python_service/
        ├── __init__.py
        ├── main.py        ← FastAPI app + route wiring
        └── api/
            ├── __init__.py
            └── health.py  ← /health endpoint (required)
```

Notice what's **not** there: a `Dockerfile`. You don't need one. CI fetches the official Dockerfile at build time.

## Step 1 — Copy the templates

From [icicle-ai/cicd-templates](https://github.com/icicle-ai/cicd-templates), grab these three files and drop them into the root of your service repo:

| File in cicd-templates | Save it as | What it's for |
|---|---|---|
| `python-uv/template.dockerignore` | `.dockerignore` | Keeps junk and secrets out of your container image |
| `icicle-service.yaml` | `icicle-service.yaml` | Your deployment config |
| `python-uv/entrypoint-template.sh` | `entrypoint.sh` | How your container starts |

Quick way to do this:

```bash
cd your-service
curl -sSL https://raw.githubusercontent.com/icicle-ai/cicd-templates/main/python-uv/.dockerignore -o .dockerignore
curl -sSL https://raw.githubusercontent.com/icicle-ai/cicd-templates/main/icicle-service.yaml -o icicle-service.yaml
curl -sSL https://raw.githubusercontent.com/icicle-ai/cicd-templates/main/python-uv/entrypoint-template.sh -o entrypoint.sh
chmod +x entrypoint.sh
```

## Step 2 — Fill out `icicle-service.yaml`

This is the single file that tells the pipeline what your service is and where to deploy it. Open it up and replace every `TODO` with real values.

Minimal example:

```yaml
schema-version: 1

# Identity
service-name: icicle-python-service        # kebab-case, becomes your docker image name
service-version: 0.1.0                # semver, becomes your docker image tag
project-name: icicle-service-project     # your team / grant / umbrella project
service-type: ai                      # one of: ai | ci | domain
pod-name: iciclepythonservice       # Tapis pod to deploy to

# Runtime
python-version: "3.13"                # MAJOR.MINOR — MUST be quoted

# System packages (leave empty lists if you don't need any)
build-apt-packages: []
runtime-apt-packages: []
```

**Things that will bite you if you're not careful:**

- **Quote `python-version`.** If you write `python-version: 3.13` unquoted, YAML parses it as a float and your build fails. Always use quotes.
- **`service-name` must be kebab-case** — lowercase letters, digits, and hyphens only, starting with a letter. It becomes a Docker image name, so the usual Docker image name rules apply.
- **`service-version` must be semver** — `MAJOR.MINOR.PATCH`, e.g. `0.1.0`. Bump this every time you release.
- **`python-version` must be compatible with your `pyproject.toml`'s `requires-python`.** More on this below.

## Step 3 — Initialize (or adopt) your uv project

ICICLE services are managed with [uv](https://docs.astral.sh/uv/). If you don't already have a `pyproject.toml` and `uv.lock`, now's the time to create them. uv's own docs are the authoritative reference — when in doubt, follow them.

### Starting from scratch (new service)

From the root of your (empty or nearly-empty) service repo, run:

```bash
uv init --package --name icicle-python-service
```

That `--package` flag is **important for ICICLE**. It tells uv to set up your project as an installable package (with a `src/` layout and a build backend), which is what the Dockerfile expects. Plain `uv init` (without `--package`) creates a simple app layout that won't install cleanly in the container — your code will build but won't be importable by `entrypoint.sh`.

What `uv init --package` creates:

- `pyproject.toml` with a build backend pre-configured
- `src/icicle_python_service/__init__.py` (stub)
- `README.md` (placeholder — replace with real content)
- `.python-version` (keep it — uv uses it for local development; ICICLE uses `icicle-service.yaml` for container builds, so they can coexist)

After that, you'll edit the generated `pyproject.toml` in Step 4.

### Adopting an existing codebase

If your service already has code and you're adding it to ICICLE:

- **Already have a `pyproject.toml` + `uv.lock`?** You're good. Skip to Step 4 and just make sure the fields match what ICICLE expects.
- **Have a `pyproject.toml` but no lockfile?** Run `uv lock` to generate one, then continue to Step 4.
- **Using `requirements.txt` or `setup.py`?** Migrate to `pyproject.toml`. Follow [uv's migration guide](https://docs.astral.sh/uv/guides/projects/). The short version: run `uv init --package --name <your-service-name>` in a clean directory, then move your deps into `[project].dependencies`.
- **No Python packaging at all?** Follow the "Starting from scratch" path above, then move your existing code under `src/<your_package>/`.

### Adding dependencies

Use `uv add` instead of hand-editing `pyproject.toml`:

```bash
uv add fastapi 'uvicorn[standard]' pydantic
uv add --dev pytest ruff                   # dev-only deps
```

`uv add` updates both `pyproject.toml` and `uv.lock` atomically. It's safer than editing by hand and forgetting to re-lock.

For anything uv-related that isn't covered here (workspace setup, alternative indexes, build backends, etc.), go to [docs.astral.sh/uv](https://docs.astral.sh/uv/). Don't guess — uv is well-documented and the patterns matter for reproducibility.

## Step 4 — Set the ICICLE fields in `pyproject.toml`

Whether uv generated your `pyproject.toml` or you already had one, a few fields must be set to specific values for ICICLE:

```toml
[project]
name = "icicle-python-service"              # MUST match icicle-service.yaml's service-name
version = "0.1.0"                      # MUST match icicle-service.yaml's service-version
requires-python = ">=3.13,<3.14"       # MUST have upper bound; MUST include python-version
dependencies = [
    "fastapi>=0.115",
    "uvicorn[standard]>=0.30",
]
```

**Keep these in sync with `icicle-service.yaml`:**

- `[project].name` ↔ `icicle-service.yaml` `service-name`
- `[project].version` ↔ `icicle-service.yaml` `service-version`
- `[project].requires-python` ↔ `icicle-service.yaml` `python-version` (the python-version must fall inside the requires-python range)

CI's validation step will yell at you if these drift apart.

---

## Step 5 — Lock your dependencies

From your service repo:

```bash
uv lock
```

This updates `uv.lock`. **Commit it.** The lockfile is what guarantees your CI build uses the same dependency versions you developed against.

You need to re-run `uv lock` any time you:

- Change `[project].dependencies` or `[dependency-groups]` by hand
- Change `requires-python`
- Want to pick up upstream dependency updates (`uv lock --upgrade`)

If you used `uv add` to add deps, the lockfile was already updated for you — no need to run `uv lock` again.

## Step 6 — Write your `entrypoint.sh`

This is how your container starts. For a typical FastAPI service:

```bash
#!/usr/bin/env sh
set -eu

# ... any pre-flight setup (migrations, env checks, etc.) ...

exec uvicorn icicle_python_service.main:app --host 0.0.0.0 --port 8000
```

Make it executable:

```bash
chmod +x entrypoint.sh
```

> ### ⚠️ You MUST use `exec` for the final long-running command
>
> The last line of `entrypoint.sh` — the one that actually starts your service — **must** begin with `exec`. This is not optional.
>
> **What `exec` does:** it replaces the shell process with your Python/uvicorn process, so your service runs as PID 1 inside the container instead of being a child of the shell.
>
> **What breaks without it:**
>
> - **Signals don't reach your service.** When Tapis (or Docker, or Kubernetes) sends SIGTERM to stop the container, the signal hits `sh`, not your Python process. `sh` typically ignores it. Your service never gets a chance to shut down cleanly, and after a grace period the runtime kills it with SIGKILL. You lose in-flight requests, open connections get severed mid-response, and any cleanup handlers you registered never run.
> - **Zombie processes accumulate.** Without `exec`, the shell stays around as PID 1 and has to reap child processes itself, which `sh` does poorly.
> - **Shutdown takes 30+ seconds instead of sub-second.** The runtime waits for the grace period to expire because it never sees a clean exit.
>
> **The rule:** any shell command that starts a long-running process (uvicorn, gunicorn, python -m your_service, celery worker, etc.) goes on its own line prefixed with `exec`. Setup steps before it (migrations, file checks) don't need `exec` — only the final process does.
>
> **Wrong:**
> ```bash
> #!/usr/bin/env sh
> set -eu
> uvicorn icicle_python_service.main:app --host 0.0.0.0 --port 8000   # ← no exec, broken
> ```
>
> **Also wrong:**
> ```bash
> #!/usr/bin/env sh
> set -eu
> exec uvicorn icicle_python_service.main:app --host 0.0.0.0 --port 8000
> echo "Service stopped"                                          # ← anything after exec is unreachable
> ```
>
> **Right:**
> ```bash
> #!/usr/bin/env sh
> set -eu
> python -m icicle_python_service.migrations                           # setup step, no exec needed
> exec uvicorn icicle_python_service.main:app --host 0.0.0.0 --port 8000   # ← final long-running command, exec required
> ```

## Step 7 — Organize your code as a proper Python package

Your service code must be structured as an **importable Python package**, not a loose collection of scripts. This matters because `entrypoint.sh` launches your service by importing a module (`uvicorn icicle_python_service.main:app`) — if your code isn't properly packaged, that import fails and the container crashes on startup.

### Use the `src/` layout

Put all your code under `src/<your_package_name>/`. The package name should match your service name with hyphens replaced by underscores (Python packages cannot contain hyphens).

| `icicle-service.yaml` service-name | Python package name |
|---|---|
| `icicle-python-service` | `icicle_python_service` |
| `ct-controller` | `ct_controller` |
| `mlflow-proxy` | `mlflow_proxy` |

### Minimum viable structure

For a small service, a single module is fine:

```
your-service/
├── icicle-service.yaml
├── pyproject.toml
├── uv.lock
├── entrypoint.sh
├── .dockerignore
└── src/
    └── icicle_python_service/
        ├── __init__.py          ← REQUIRED, even if empty
        └── main.py
```

The `__init__.py` is what makes the directory a Python package. It can be empty — what matters is that it exists. Without it, `from icicle_python_service.main import app` silently fails to find your code.

### As your service grows, use submodules

Anything beyond "one file with a FastAPI app" should be broken up. A typical shape:

```
src/
└── icicle_python_service/
    ├── __init__.py
    ├── main.py                 ← FastAPI app + route wiring
    ├── config.py               ← settings / env vars (e.g. pydantic-settings)
    ├── api/
    │   ├── __init__.py
    │   ├── health.py           ← health endpoints
    │   └── detection.py        ← your service's actual endpoints
    ├── models/
    │   ├── __init__.py
    │   └── schemas.py          ← Pydantic request/response models
    └── services/
        ├── __init__.py
        └── detector.py         ← your business logic
```

Every directory under `src/icicle_python_service/` needs its own `__init__.py`. Imports then look like:

```python
# src/icicle_python_service/main.py
from fastapi import FastAPI
from icicle_python_service.api import health, detection
from icicle_python_service.config import settings

app = FastAPI(title=settings.service_name)
app.include_router(health.router)
app.include_router(detection.router)
```

### Make sure your `pyproject.toml` uses the uv build backend

Your `pyproject.toml` should declare `uv_build` as the build backend. This is what lets `uv sync` (both locally and in the container) install your own code into the venv so it's importable at runtime. If you created the project with `uv init --package`, this is already set for you. Verify or add:

```toml
[build-system]
requires = ["uv_build>=0.11.7,<0.12.0"]
build-backend = "uv_build"
```

You don't need to add any `[tool.hatch.*]` or `[tool.setuptools.*]` config — uv's build backend auto-discovers packages under `src/` using your project name. Just keep the directory name under `src/` matching your project's package name (hyphens → underscores), and it works.

> **Note:** "build backend" here doesn't mean we're publishing your service to PyPI or anywhere else. It's just what lets the container install your code so `entrypoint.sh` can import it. ICICLE services don't get published as packages.

### Verify it actually works before pushing

Imports that work in your editor don't always work in the container. Test the full install-and-import path locally **before** pushing:

```bash
# From your service repo root
uv sync                                       # installs your package into .venv
uv run python -c "from icicle_python_service.main import app; print(app.title)"
```

If that command prints your app title, your package is importable. If it raises `ModuleNotFoundError`, something's wrong with your structure — most commonly a missing `__init__.py` or a mismatch between your package name and what `entrypoint.sh` is trying to import.

Also test that the exact string in your `entrypoint.sh` resolves:

```bash
# Replace with your own module:app reference from entrypoint.sh
uv run uvicorn icicle_python_service.main:app --host 127.0.0.1 --port 8000
```

If uvicorn starts and serves requests, CI will too. If it fails here, it'll fail in the container.

### Common structural mistakes

- **Missing `__init__.py`** in one or more directories. Every folder under `src/<package>/` needs one.
- **Hyphens in Python package names.** `icicle-python-service` is a valid service name but not a valid Python package name. Use `icicle_python_service` for the directory under `src/`.
- **Code living at the repo root instead of under `src/`.** Works on your machine because of Python's path behavior, breaks in the container because the container installs your package, not your repo.
- **Importing with relative paths that only work when you run from a specific directory.** Use absolute imports (`from icicle_python_service.config import settings`), not relative hacks (`from ..config import settings` outside package boundaries).
- **Directory under `src/` doesn't match the project name.** `uv_build` finds your package by matching the project name (with hyphens → underscores) against directory names under `src/`. If they disagree, the built wheel is empty and imports fail at runtime.

## Step 8 — Implement a `/health` endpoint

Every ICICLE service **must** expose an HTTP `GET /health` endpoint. This is how the platform and on-call engineers verify that your service is alive, that the right version was deployed, and (when you add checks) that its dependencies are reachable.

The deploy pipeline is fire-and-forget — it tells Tapis to roll out your image and returns success. It does **not** verify that your service actually started cleanly or that the correct version is serving traffic. Your `/health` endpoint is how you close that loop.

### Minimum required response

```json
{
  "status": "ok",
  "service": "icicle-python-service",
  "version": "0.1.5",
  "build_sha": "8f3c2a1",
  "timestamp": "2026-04-23T18:30:00Z"
}
```

Four fields, all required:

- **`status`** — `"ok"` when the service is healthy, `"degraded"` or `"error"` if something's wrong. Keep this binary for the top-level — use the details below for nuance.
- **`service`** — your service name, matching `icicle-service.yaml`. Helps when multiple services reply to the same hostname via a reverse proxy.
- **`version`** — the running service's version. This is how we verify the right code got deployed. Read it from your package metadata, not a hardcoded string (see below).
- **`build_sha`** — the short git SHA of the commit CI built from. Read it from an environment variable the container sets at build time.
- **`timestamp`** — ISO 8601 UTC. Confirms the service is actually responding now and not returning a cached response.

### Template implementation

Create `src/icicle_python_service/api/health.py`:

```python
from datetime import datetime, timezone
from importlib.metadata import version, PackageNotFoundError
import os

from fastapi import APIRouter

router = APIRouter()

# Read the version from installed package metadata — same value as
# [project].version in pyproject.toml. No hardcoded strings.
try:
    SERVICE_VERSION = version("icicle-python-service")
except PackageNotFoundError:
    SERVICE_VERSION = "unknown"

# Set by the Dockerfile at build time via ENV BUILD_SHA.
BUILD_SHA = os.environ.get("BUILD_SHA", "unknown")

SERVICE_NAME = "icicle-python-service"


@router.get("/health")
def health() -> dict:
    """Liveness + version check. Must stay fast and dependency-free."""
    return {
        "status": "ok",
        "service": SERVICE_NAME,
        "version": SERVICE_VERSION,
        "build_sha": BUILD_SHA,
        "timestamp": datetime.now(timezone.utc).isoformat(),
    }
```

Wire it into your FastAPI app in `src/icicle_python_service/main.py`:

```python
from fastapi import FastAPI
from icicle_python_service.api import health

app = FastAPI()
app.include_router(health.router)
```

### Verifying the right version was deployed

After a deploy, hit your service's `/health` endpoint (the URL is printed by the deploy pipeline):

```bash
curl https://<your-service-url>/health
```

Confirm:

- `version` matches the `service-version` you just deployed in `icicle-service.yaml`.
- `build_sha` matches the git commit you pushed (short SHA).

If either is stale, your pod didn't pick up the new image — open an issue in `#icicle-service-support`.

### Adding more checks

The `/health` endpoint shown above is **liveness** only: "is the process running and responding?" Keep it dependency-free so it always returns quickly — a liveness check that queries a database can fail to return during DB slowness and make your service look unhealthy when it's fine.

For **readiness** (is your service ready to serve traffic?) or **dependency checks** (can it reach the database, object store, etc.), add a separate `/ready` endpoint:

```python
@router.get("/ready")
def ready() -> dict:
    checks = {
        "database": check_database(),
        "s3": check_object_store(),
        "downstream_api": check_downstream(),
    }
    all_ok = all(checks.values())
    return {
        "status": "ok" if all_ok else "degraded",
        "service": SERVICE_NAME,
        "version": SERVICE_VERSION,
        "build_sha": BUILD_SHA,
        "timestamp": datetime.now(timezone.utc).isoformat(),
        "checks": {k: ("ok" if v else "fail") for k, v in checks.items()},
    }
```

Keep `/health` fast and dumb. Put everything that can block, timeout, or depend on external systems behind `/ready`.

## Step 9 — Test your build locally (optional but recommended)

Before pushing, make sure your container actually builds. Fetch the official Dockerfile and build it locally.

### Simple case: no system packages

For a service that only needs Python and its dependencies:

```bash
# Grab the official Dockerfile — temporary, for local testing only
curl -sSL https://raw.githubusercontent.com/icicle-ai/cicd-templates/main/Dockerfile -o Dockerfile

# Build it, passing the same args CI would pass (empty apt lists)
docker build \
  --build-arg PYTHON_VERSION=3.13 \
  --build-arg BUILD_APT_PACKAGES="" \
  --build-arg RUNTIME_APT_PACKAGES="" \
  -t icicle-python-service:test .

# Run it and hit the health endpoint
docker run --rm -p 8000:8000 icicle-python-service:test

# In another terminal:
curl http://localhost:8000/health
```

### With system packages

If your service needs system libraries (compiled dependencies, native tools, etc.), pass them as space-separated strings in the build args. The distinction between **build** and **runtime** packages matters:

```bash
docker build \
  --build-arg PYTHON_VERSION=3.13 \
  --build-arg BUILD_APT_PACKAGES="build-essential pkg-config libpq-dev" \
  --build-arg RUNTIME_APT_PACKAGES="ca-certificates libpq5" \
  -t icicle-python-service:test .
```

> ### Build vs. runtime apt packages — what's the difference?
>
> The Dockerfile has two stages: a **build stage** (where dependencies are compiled and installed) and a **run stage** (the final image that actually ships to production). Each stage has its own apt package list, and they serve different purposes.
>
> **`BUILD_APT_PACKAGES`** are installed in the build stage only. Use this for things you need *during* `uv sync` — typically compilers and headers required to build Python packages from source.
>
> - Examples: `build-essential` (gcc/g++), `pkg-config`, `libpq-dev` (PostgreSQL *headers*, for building `psycopg2`), `python3-dev`, `cmake`, `libssl-dev`
> - Rule of thumb: if it's a `-dev` package, a compiler, or a build tool, it goes here.
> - These do **not** end up in your final image — they're left behind in the build stage.
>
> **`RUNTIME_APT_PACKAGES`** are installed in the run stage and ship in your final image. Use this for things your service needs *while running*.
>
> - Examples: `ca-certificates` (for outbound HTTPS), `libpq5` (PostgreSQL *client library*, what psycopg2 links against at runtime), `curl`, `libxml2`, `libjpeg62-turbo`
> - Rule of thumb: if it's a shared library your Python deps link to, or a binary your service calls via subprocess, it goes here.
> - Keep this list **short**. Every package here increases your image size and attack surface.
>
> **A common pairing** — to use `psycopg2` (PostgreSQL driver):
>
> ```yaml
> build-apt-packages:
>   - build-essential     # to compile psycopg2 from source
>   - libpq-dev           # headers psycopg2 needs at compile time
>
> runtime-apt-packages:
>   - libpq5              # the shared library psycopg2 links to at runtime
> ```
>
> Note: `libpq-dev` in build, `libpq5` in runtime. The `-dev` package is for compilation; the non-dev package contains the actual `.so` file your code loads.
>
> **When in doubt:** if a package has a `-dev` counterpart, put the `-dev` version in build and the non-dev version in runtime. If it doesn't (e.g., `ca-certificates`), it's almost always runtime-only.

### After testing

```bash
# Verify health endpoint reports the right version
curl http://localhost:8000/health
# Expected: {"status":"ok","service":"icicle-python-service","version":"0.1.0",...}
```

> ### ⚠️ DO NOT MODIFY the Dockerfile
>
> The Dockerfile is owned by the ICICLE platform team and is the source of truth for how your service gets built. CI will **always overwrite** any local changes at build time — editing it locally will not affect your deploys, and committing a modified version to your repo will not either.
>
> If the official Dockerfile doesn't meet your needs, see [When you need something the template doesn't support](#when-you-need-something-the-template-doesnt-support) at the end of this doc.
>
> After local testing, you can `rm Dockerfile` or leave it — either way, CI ignores whatever's there and fetches its own copy.

## Step 10 — Commit and push

```bash
git add icicle-service.yaml pyproject.toml uv.lock entrypoint.sh .dockerignore src/
git commit -m "initial ICICLE service setup"
git push
```

CI will pick it up automatically. Watch the pipeline — if something's wrong with your `icicle-service.yaml` or `pyproject.toml`, it'll fail at the validation step with a readable error message telling you what to fix.

## Day-to-day: updating your service

Once the initial setup is done, the normal flow is:

1. Change your code.
2. Bump `service-version` in `icicle-service.yaml` AND `version` in `pyproject.toml` (they must stay in sync).
3. If you changed dependencies, re-run `uv lock`.
4. Commit and push.

CI handles the rest.

---

## Where to check on deploys

After CI finishes, it prints URLs in the final step of the pipeline:

- **Your service's `/health` endpoint** — the fastest way to verify the deploy worked. Hit it, check that `version` and `build_sha` in the response match what you just pushed.
- **Status URL** — live status of your Tapis pod (Tapis-level, not service-level).
- **Logs URL** — streaming logs from your running container.

Bookmark these for your service. The pipeline is fire-and-forget; it doesn't wait for your pod to come up. You're responsible for checking `/health` to confirm a successful rollout.

> **Tip:** if `/health` returns the old `version`, your pod is still serving the previous image. Wait 30–60 seconds for rollout, then retry. If it stays stale for more than a few minutes, check the logs URL and ping `#icicle-service-support`.

## Common problems

**`uv.lock` is missing**
Run `uv lock` and commit the result.

**Validation fails with "python-version must be a string"**
You forgot to quote it in `icicle-service.yaml`. Change `python-version: 3.13` to `python-version: "3.13"`.

**Validation fails with "python-version not compatible with requires-python"**
Your `icicle-service.yaml` and `pyproject.toml` disagree. Example: `icicle-service.yaml` says `"3.13"` but `pyproject.toml` says `requires-python = ">=3.14,<3.15"`. Fix one of them so they agree.

**Build fails at `apt-get install`**
A package name in your `build-apt-packages` or `runtime-apt-packages` is wrong. Check the Debian package name exactly.

**Build succeeds, but pod doesn't come up**
The pipeline doesn't verify rollout. Check your Tapis status/log URLs. Most often this is an entrypoint or port issue.

**`/health` returns `"version": "unknown"`**
Your service can't find its own package metadata. Most commonly: the package name in `importlib.metadata.version("...")` doesn't match `[project].name` in `pyproject.toml`, or the package isn't installed in the venv (check your `src/` layout and `uv_build` config).

**`/health` returns `"build_sha": "unknown"`**
CI isn't passing `BUILD_SHA` as a build arg, or the Dockerfile isn't setting it as an ENV. If you're testing locally, this is expected — `BUILD_SHA` only gets set during CI builds. In production, ping `#icicle-service-support`.

**`/health` returns a version that's one behind what I pushed**
Your pod hasn't picked up the new image yet. Wait 30–60 seconds. If it stays stale, the image may have failed to pull, or the deploy request was dropped — check logs and status URLs.

## When you need something the template doesn't support

The official Dockerfile handles the common case: a Python service using uv, optionally with some apt packages, running a single entrypoint. If your service needs something outside that — a custom base image, GPU support, multi-stage builds with weird caching, compiled Rust extensions, whatever — we'd rather hear about it than have you fork the template.

**Open an issue** in [icicle-ai/cicd-templates](https://github.com/icicle-ai/cicd-templates/issues) describing what you need and why, and ping **`#icicle-service-support`** on Slack. We'll either accommodate it by extending the template for everyone, or work out a one-off solution for your service.

**Please do not:**

- Fork the Dockerfile and commit a modified version to your service repo (CI overwrites it anyway).
- Add your own build pipeline in parallel (your service won't get platform updates).
- Work around the template with creative entrypoint hacks (if it's hacky, file an issue — we probably want to fix it properly).
