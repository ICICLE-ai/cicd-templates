# Setting Up an ICICLE Python Service

> Step-by-step instructions for onboarding a new Python service to ICICLE's CI/CD pipeline.

This guide walks you through everything you need in your service repo to get it building and deploying automatically.

The examples use FastAPI and Uvicorn. Other Python web frameworks can use the same template if they provide the required API and health routes, listen on the configured port, and start through `entrypoint.sh`.

Not a Python service? See [`node-backend/service-setup.md`](../node-backend/service-setup.md) for Node API servers, or [`node-frontend/service-setup.md`](../node-frontend/service-setup.md) for React/Vue/Svelte SPAs.

---

## Before you start

You'll need:

- A service repository authorized to use ICICLE's shared deployment credentials. Coordinate repository access with the platform team.
- [`uv`](https://docs.astral.sh/uv/) installed locally.
- Docker installed locally (for optional local testing).
- **An existing Tapis pod** with networking and registry access configured. CI updates its image, restarts it, and verifies the build SHA; it does not create the pod. See [deployment prerequisites and verification](../README.md#deployment-and-verification).
- Access to the [deployment secrets](../README.md#deployment-and-verification) passed by the reusable-workflow caller. The organization normally provides the Tapis and registry credentials.

## What you're building

By the end of this guide, your service repo will have:

```
your-service/
├── .github/
│   └── workflows/
│       └── deploy.yaml        ← calls the ICICLE reusable workflow
├── icicle-service.yaml        ← deploy config (you create)
├── pyproject.toml             ← Python dependencies + packaging config
├── uv.lock                    ← generated by uv
├── entrypoint.sh              ← how your container starts (you create)
├── .dockerignore              ← copied from the template
└── src/
    └── icicle_python_service/
        ├── __init__.py
        ├── main.py            ← FastAPI app + route wiring
        └── api/
            ├── __init__.py
            └── health.py      ← /health endpoint (required)
```

Notice what's **not** there: a `Dockerfile`. You don't need one. CI fetches the official Dockerfile at build time.

## Step 1 — Copy the templates

From [icicle-ai/cicd-templates](https://github.com/icicle-ai/cicd-templates), grab these files into the root of your service repo:

| File in cicd-templates | Save it as | What it's for |
|---|---|---|
| `python/.dockerignore` | `.dockerignore` | Keeps junk and secrets out of your container image |
| `icicle-service.yaml` | `icicle-service.yaml` | Your deployment config (empty starter) |
| `python/entrypoint.sh` | `entrypoint.sh` | How your container starts |
| `deploy.yaml` | `.github/workflows/deploy.yaml` | The workflow that wires CI to ICICLE's pipeline |

Quick way to do this:

```bash
cd your-service

mkdir -p .github/workflows

TEMPLATES_REF=main  # Current development version; choose a reviewed release/commit for production.
BASE="https://raw.githubusercontent.com/icicle-ai/cicd-templates/$TEMPLATES_REF"
curl -fsSL "$BASE/python/.dockerignore" -o .dockerignore
curl -fsSL "$BASE/icicle-service.yaml"  -o icicle-service.yaml
curl -fsSL "$BASE/python/entrypoint.sh" -o entrypoint.sh
curl -fsSL "$BASE/deploy.yaml"          -o .github/workflows/deploy.yaml

chmod +x entrypoint.sh
```

The workflow you just copied triggers on pushes to `main` and on manual dispatch from the Actions tab. The current starter calls the reusable workflow at `@main`, which follows unreleased development changes. For production, select a reviewed release or commit and update both `TEMPLATES_REF` above and the workflow's `uses: ...@ref` to match. The Dockerfile, shared runtime files, and workflow share one template release; `schema-version` and your application's `service-version` are separate. See [Versioning](../README.md#versioning).

For reference, see the [annotated config example](../icicle-service-example.yaml) from the same template version.

## Step 2 — Fill out `icicle-service.yaml`

This is the single file that tells the pipeline what your service is and where to deploy it. Open it up and replace each blank with a real value.

Minimal example:

```yaml
schema-version: 2

# Identity
service-name: iciclepythonservice          # image basename; must equal pod-name
service-version: 0.1.0                     # semver, becomes your docker image tag
project-name: icicle-service-project       # your team / grant / umbrella project
service-type: ai                           # one of: ai | ci | domain
pod-name: iciclepythonservice              # Tapis pod to deploy to

# Runtime
runtime-type: python                       # one of: python | node-backend | node-frontend
runtime-version: "3.13"                    # MAJOR.MINOR — MUST be quoted
include-dev-dependencies: false            # New services: omit the dev group at runtime

# System packages (leave empty lists if you don't need any)
build-apt-packages: []
runtime-apt-packages: []
```

New services must use schema 2: `service-name` and `pod-name` are both `iciclepythonservice` in this example. Use 4–64 lowercase letters/digits, starting with a letter, and provision that pod before deploying. Package names, repository names, and `project-name` can differ. Existing schema 1 services can keep their names; see [migration guidance](../README.md#configuration-and-compatibility).

See the [shared configuration contract](../README.md#shared-service-requirements) for name formats, typed fields, optional deployment settings, and schema compatibility. Keep the quoted Python version compatible with `requires-python` and your development environment.

## Step 3 — Initialize (or adopt) your uv project

ICICLE Python services are managed with [uv](https://docs.astral.sh/uv/). If you don't already have a `pyproject.toml` and `uv.lock`, now's the time to create them. uv's own docs are the authoritative reference — when in doubt, follow them.

### Starting from scratch (new service)

From the root of your (empty or nearly-empty) service repo, run:

```bash
uv init --package --name icicle-python-service
```

The `--package` flag creates an installable package with a `src/` layout and build backend, matching the examples in this guide. Plain `uv init` creates a non-package application; add packaging configuration if you want to use the installed-package metadata and imports shown below. The Dockerfile runs `uv sync`, which uses your project's chosen build backend.

What `uv init --package` creates:

- `pyproject.toml` with a build backend pre-configured
- `src/icicle_python_service/__init__.py` (stub)
- `README.md` (placeholder — replace with real content)
- `.python-version` (selects the local development interpreter; keep it compatible with `runtime-version`)

After that, you'll edit the generated `pyproject.toml` in Step 4.

### Adopting an existing codebase

Keep an existing uv-compatible `pyproject.toml`, build backend, and source layout. Generate or update `uv.lock` with `uv lock`. The template requires those two files and an `entrypoint.sh`; it does not require `uv_build`, FastAPI, a `src/` directory, or a particular module name.

If you currently use a different dependency format, follow [uv's project guide](https://docs.astral.sh/uv/guides/projects/) to produce a project and lockfile. An installable package makes the metadata example below convenient; a non-package application can expose equivalent version metadata another way.

### Adding dependencies

For example, add runtime and development dependencies with:

```bash
uv add fastapi 'uvicorn[standard]' pydantic
uv add --dev pytest ruff                   # development dependency group
```

`uv add` updates the project and lockfile together. If you edit dependencies manually, run `uv lock` before building.

Build dependencies can use the dev group during the build. New services should set `include-dev-dependencies: false`, as the starter does, to omit that group from the final environment. Put runtime imports in project dependencies before enabling this setting. Existing configurations that omit it preserve the previous behavior and retain the dev group; explicit `true` also retains it.

See [uv documentation](https://docs.astral.sh/uv/) for workspaces, alternative indexes, and build backends.

## Step 4 — Set the ICICLE fields in `pyproject.toml`

For the installable package example:

```toml
[project]
name = "icicle-python-service"             # Package name used by importlib.metadata
version = "0.1.0"                          # Package version; deployment uses service-version
requires-python = ">=3.13,<3.14"           # Example supported range; MUST include runtime-version
dependencies = [
    "fastapi>=0.115",
    "uvicorn[standard]>=0.30",
]
```

Use the actual package name when reading `importlib.metadata.version()`; it may differ from the container's `service-name`. CI provides the deployed `service-version` as `BUILD_VERSION`; your package version can follow its own release process. CI validates `icicle-service.yaml`, while uv validates the Python project and lockfile during the build.

Both container sync steps select `PYTHON_VERSION` explicitly, so `.python-version` does not silently select a different container interpreter. `requires-python` must allow that configured runtime. An upper bound is optional. Keep `.python-version` consistent with your intended local runtime; see [uv's Python selection rules](https://docs.astral.sh/uv/concepts/python-versions/#project-python-versions).

## Step 5 — Lock your dependencies

From your service repo:

```bash
uv lock
```

This updates `uv.lock`. **Commit it.** The lockfile is what guarantees your CI build uses the same dependency versions you developed against.

You need to re-run `uv lock` any time you:

- Change `[project].dependencies` or `[dependency-groups]` by hand
- Change project metadata, including `[project].version`
- Change `requires-python`
- Want to pick up upstream dependency updates (`uv lock --upgrade`)

If you used `uv add` to add deps, the lockfile was already updated for you — no need to run `uv lock` again.

## Step 6 — Write your `entrypoint.sh`

This is how your container starts. For a typical FastAPI service:

```bash
#!/usr/bin/env sh
set -eu

# ... any pre-flight setup (migrations, env checks, etc.) ...

exec uvicorn icicle_python_service.main:app --host 0.0.0.0 --port 8000
```

Make it executable:

```bash
chmod +x entrypoint.sh
```

The image invokes this file as `sh entrypoint.sh`, so use POSIX shell syntax. Listen on `0.0.0.0`, and configure the Tapis pod's networking port to match your application's port (`8000` in these examples).

End the script with `exec` so the server receives container stop signals directly. Run initialization before it. The server must handle shutdown within the platform's termination grace period; see the [shared startup contract](../README.md#shared-service-requirements).

## Step 7 — Connect your application routes

Choose any source layout supported by your build backend. For the `uv init --package` example, the entrypoint imports `icicle_python_service.main:app` from `src/icicle_python_service/main.py`. Regular packages use `__init__.py`; other layouts need corresponding packaging configuration.

A FastAPI application can keep operational health separate from application routes:

```python
from fastapi import FastAPI
from icicle_python_service.api import health, tasks

app = FastAPI()
app.include_router(health.router)
app.include_router(tasks.router, prefix="/api")
```

A `@router.get("/tasks")` route becomes `/api/tasks`. New frontend clients must request same-origin relative `/api/...` paths. The shared frontend proxy preserves that complete path and query string, so add the prefix once in the backend. `/health` stays outside it. This applies to other Python frameworks too; see the [API contract](../README.md#shared-service-requirements) and [frontend proxy setup](../node-frontend/service-setup.md#step-5--config-and-api-urls).

Check that your actual entrypoint imports work after a locked install:

```bash
uv sync --locked
uv run python -c "from icicle_python_service.main import app; print(app.title)"
```

If imports fail, check the build backend's package discovery, module names, and installed dependencies. Test the final image as well, since its production dependencies and networking differ from your development environment.

## Step 8 — Implement a `/health` endpoint

Every ICICLE Python service **must** expose an HTTP `GET /health` endpoint. Keep it outside the `/api` prefix. This is how the platform and on-call engineers verify that your service is alive and that the expected version is running. Static frontends instead expose `/healthcheck` through nginx.

CI updates the pod image and verifies that `/health` returns the expected `build_sha`. Other health metadata remains useful for operators; keep the endpoint fast and dependency-free.

### Example response

```json
{
  "status": "ok",
  "service": "iciclepythonservice",
  "version": "0.1.0",
  "build_sha": "0123456789abcdef0123456789abcdef01234567",
  "timestamp": "2026-04-23T18:30:00Z"
}
```

The shared [health contract](../README.md#deployment-and-verification) describes what CI verifies. Return `status: "ok"` and the full `BUILD_SHA` supplied by the image; service, version, and timestamp also make manual diagnosis useful. Keep this endpoint fast and avoid caching it.

### Template implementation

Create `src/icicle_python_service/api/health.py`:

```python
from datetime import datetime, timezone
from importlib.metadata import version, PackageNotFoundError
import os

from fastapi import APIRouter

router = APIRouter()

# CI supplies the deployed version; local runs can use package metadata.
try:
    SERVICE_VERSION = os.environ.get("BUILD_VERSION") or version("icicle-python-service")
except PackageNotFoundError:
    SERVICE_VERSION = "unknown"

# Set by the Dockerfile at build time via ENV BUILD_SHA.
BUILD_SHA = os.environ.get("BUILD_SHA", "unknown")

SERVICE_NAME = "iciclepythonservice"


@router.get("/health")
def health() -> dict:
    """Liveness + version check. Must stay fast and dependency-free."""
    return {
        "status": "ok",
        "service": SERVICE_NAME,
        "version": SERVICE_VERSION,
        "build_sha": BUILD_SHA,
        "timestamp": datetime.now(timezone.utc).isoformat(),
    }
```

Wire it into your FastAPI app in `src/icicle_python_service/main.py`:

```python
from fastapi import FastAPI
from icicle_python_service.api import health

app = FastAPI()
app.include_router(health.router)
```

### Verify locally and after deployment

```bash
curl http://localhost:8000/health
```

For an image built with `BUILD_SHA=local-test`, expect that value in `build_sha`. See [deployment verification](../README.md#deployment-and-verification) for CI's rollout checks and failure diagnostics.

### Adding more checks

The `/health` endpoint shown above is **liveness** only: "is the process running and responding?" Keep it dependency-free so it always returns quickly — a liveness check that queries a database can fail to return during DB slowness and make your service look unhealthy when it's fine.

For **readiness** (is your service ready to serve traffic?) or **dependency checks** (can it reach the database, object store, etc.), add a separate `/ready` endpoint:

```python
@router.get("/ready")
def ready() -> dict:
    checks = {
        "database": check_database(),
        "s3": check_object_store(),
        "downstream_api": check_downstream(),
    }
    all_ok = all(checks.values())
    return {
        "status": "ok" if all_ok else "degraded",
        "service": SERVICE_NAME,
        "version": SERVICE_VERSION,
        "build_sha": BUILD_SHA,
        "timestamp": datetime.now(timezone.utc).isoformat(),
        "checks": {k: ("ok" if v else "fail") for k, v in checks.items()},
    }
```

Keep `/health` fast and dumb. Put everything that can block, timeout, or depend on external systems behind `/ready`.

## Step 9 — Test your build locally (optional but recommended)

Before pushing, make sure your container actually builds. Fetch the official Dockerfile and build it locally.

### Simple case: no system packages

For a service that only needs Python and its dependencies:

```bash
# Grab the official Dockerfile — temporary, for local testing only
TEMPLATES_REF=main  # Match the ref in your service's reusable-workflow call.
curl -fsSL "https://raw.githubusercontent.com/icicle-ai/cicd-templates/$TEMPLATES_REF/python/Dockerfile" -o Dockerfile

# Build it, passing the same args CI would pass (empty apt lists)
docker build \
  --build-arg PYTHON_VERSION=3.13 \
  --build-arg INCLUDE_DEV_DEPENDENCIES=false \
  --build-arg BUILD_APT_PACKAGES="" \
  --build-arg RUNTIME_APT_PACKAGES="" \
  --build-arg BUILD_SHA=local-test \
  -t iciclepythonservice:test .

# Run it and hit the health endpoint
docker run --rm -p 8000:8000 iciclepythonservice:test

# In another terminal:
curl http://localhost:8000/health
# Check one of your implemented application API routes too, for example:
curl http://localhost:8000/api/tasks
```

These manual builds explicitly select the new-service production setting. CI passes `INCLUDE_DEV_DEPENDENCIES` from `include-dev-dependencies`; omitting that config field preserves the legacy `true` default.

### With system packages

If your service needs system libraries (compiled dependencies, native tools, etc.), pass them as space-separated strings in the build args. The distinction between **build** and **runtime** packages matters:

```bash
docker build \
  --build-arg PYTHON_VERSION=3.13 \
  --build-arg INCLUDE_DEV_DEPENDENCIES=false \
  --build-arg BUILD_APT_PACKAGES="build-essential pkg-config libpq-dev" \
  --build-arg RUNTIME_APT_PACKAGES="ca-certificates libpq5" \
  --build-arg BUILD_SHA=local-test \
  -t iciclepythonservice:test .
```

Install compilers and headers with `build-apt-packages`; install shared libraries and commands needed by the running service with `runtime-apt-packages`. For example, building `psycopg2` from source can require `build-essential` and `libpq-dev` during build, and `libpq5` at runtime. Package names must match the image's Debian release. Leave unused lists empty.

### After testing

```bash
# Verify health endpoint reports the right version
curl http://localhost:8000/health
# Expected: {"status":"ok","service":"icicle-python-service","version":"0.1.0","build_sha":"local-test",...}
```

Remove the downloaded Dockerfile after local testing if you do not need it. CI fetches the authoritative copy from this shared repository.

## Step 10 — Commit and push

```bash
git status --short
# Stage the service files you intend to commit.
git diff --cached
git commit -m "initial ICICLE service setup"
git push
```

Review staged changes before committing; keep local environments, dependencies, generated downloads, and secrets out of the commit.

CI will pick it up automatically. Open the **Actions** tab in your service repo on GitHub to watch the deploy run. If something's wrong with your `icicle-service.yaml`, it'll fail at the validation step with a readable error message telling you what to fix. uv validates the project and lockfile during the build; CI verifies the running build SHA after deployment.

## Day-to-day: updating your service

Once the initial setup is done, the normal flow is:

1. Change your code.
2. Set the deployed release's `service-version` in `icicle-service.yaml`.
3. Run `uv lock` after changing the project version or dependencies, and commit `uv.lock`.
4. Commit and push; CI builds, updates the pod image, and verifies the running build SHA.
5. Inspect the deployment result and exercise your application routes.

Runtime environment, networking, and registry access remain platform-managed; CI changes the image and verifies rollout.

---

## Where to check on deploys

The Actions run records the built image and digest, pod state changes, and verification result. A successful run adds the deployed and previous image references to its summary. See [deployment diagnostics](../README.md#deployment-and-verification) for the Tapis status and logs endpoints.

A stale `build_sha` fails verification. Check pod startup and image pull errors, the health URL, and whether a proxy is serving a cached response.

## Common problems

**`uv.lock` is missing**
Run `uv lock` and commit the result.

**Validation fails with "runtime-version must be MAJOR.MINOR"**
Use a quoted major/minor string, such as `runtime-version: "3.13"`. A bare major version is invalid. Numeric YAML values can also change during parsing: `3.10` can become `3.1`.

**Validation fails for `service-name` or `pod-name`**
Schema 2 requires both values to equal the existing pod's ID: 4–64 lowercase letters and digits, starting with a letter. `api1` is valid; `api`, `1api`, `MyApi`, `my-api`, and `my api` are invalid. Schema 1 retains its legacy service-name rules. Changing this file does not rename a pod.

**Build fails at `apt-get install`**
A package name in your `build-apt-packages` or `runtime-apt-packages` is wrong. Check the Debian package name exactly — these install on Debian Trixie, not Ubuntu, and not all package names are identical.

**Build succeeds, but pod doesn't come up**
CI fails the rollout check. Inspect the pod logs and status for an entrypoint, dependency, or port issue, and verify the health endpoint is reachable from the Actions runner.

**`/health` returns `"version": "unknown"`**
`BUILD_VERSION` is empty and the fallback cannot find package metadata. Check that `importlib.metadata.version("...")` uses the installed distribution's name, and that your build backend installs that package into the environment.

**`/health` returns `"build_sha": "unknown"`**
CI isn't passing `BUILD_SHA` as a build arg, or the Dockerfile isn't setting it as an ENV. If you're testing locally, this is expected unless you passed `--build-arg BUILD_SHA=...` yourself. In production, ping `#icicle-service-support`.

**`/health` returns a version that's one behind what I pushed**
Check `build_sha` first: CI verifies that value, while older applications may still report a package version. Prefer `BUILD_VERSION` in your version field. A stale SHA indicates a rollout, routing, or caching problem and fails deployment verification.
